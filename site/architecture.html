Architecture

How a versioned task and an agent become a scored, replayable trace.

status: Milestone 7 — tasks, tools, the runtime loop, structured tracing, trace replay, and sandbox controls implemented; full scoring pending

Brief explanation

The runtime is an explicit pipeline. Each stage has a clear input and output so that every step can be inspected, traced, and reproduced.

Design principles: deterministic-first, everything-is-traced, separation of policy and mechanism, and no hidden cost.

Core tools (Milestone 3)

Tools are the only way an agent acts on a workspace. Every tool shares one shape — a static ToolSpec, a validated run() entry point, and a JSON-serialisable ToolResult — so the runtime can dispatch them uniformly and the tracer can record them faithfully. A ToolRegistry maps names to tools and dispatches a ToolCall. Path-taking tools are confined to one workspace directory; subprocess tools bound their output and time and run without a shell.

ToolCategoryWhat it returns
read_filereadcontent, bytes, lines, binary/truncated flags
search_reporeadmatching lines (path/line/text), counts
git_diffreadunified diff, per-file +/- counts, untracked files
write_filewritebytes written, created vs. overwrote
apply_patchwriteper-file create/modify/delete, +/- counts
run_shellexecargv, exit code, stdout/stderr, timed-out flag
run_testsexecas run_shell, plus a passed boolean

The registry's REGISTERED_TOOL_NAMES is the authoritative tool vocabulary; a test asserts it equals the task schema's KNOWN_TOOLS, so a task can never request a tool that does not exist.

Runtime loop (Milestone 4)

The runtime turns a validated task and an agent into a single structured, scored RunResult. An agent only proposes the next action (run a tool, or finish); the runtime owns every side effect — preparing the workspace, gating each call against the task's allowed_tools, dispatching it, running the task's test command, capturing the final diff, scoring, and reporting. Two deterministic, model-free agents ship: mock (a null baseline that does nothing) and scripted (replays a fixed plan, with built-in solutions for the example tasks). Run one with code-agent-runtime run <task>.

load task -> prepare workspace -> [agent step -> gate -> execute tool]* -> run tests -> score -> report
StageWhat happens

Containment is workspace confinement, allowed_tools capability gating, and the Milestone 7 sandbox policy (see below) — but no process/namespace isolation. Scoring is intentionally minimal; the full scorer, suite runner, and reports are Milestone 8.

Trace recorder (Milestone 5)

A run can be recorded as a structured, JSON-serialisable Trace with two layers: a timestamped events timeline (run_started, workspace_prepared, tool_call, agent_finish, tests_ran, diff_captured, scored, run_finished) and the embedded result holding the full payloads (command stdout/stderr, the final diff, test results, exit status). The recorder owns the when — each event carries a wall-clock timestamp and a monotonic elapsed_seconds; the run carries started_at/finished_at/ duration_seconds. This is the one temporal artifact: tools and RunResult stay timing-free and deterministic. Tracing is opt-in — the loop records only when a recorder is passed (run_task(..., recorder=) / record_run / run --trace) — and the loop never imports the tracer, so an untraced run is unchanged. Captured output is not redacted yet (Milestone 7).

Trace replay (Milestone 6)

replay_trace(trace) reconstructs a run from a stored trace without re-executing it, into a ReplayedRun: the ordered timeline, the tool_calls extracted from it, the tests and diff payloads, every detected anomaly (a blocked or failed tool call, a failing test command, a run that errored), and the single failure point that best explains the verdict — a terminal run_error, then the scoring tests_failed, else the earliest anomaly. A run that passed or was not scored has no failure point, even with anomalies: that asymmetry surfaces a verdict that hid a failure mode. Two renderers print a reconstruction — summarize_trace (text) and trace_to_markdown (a Markdown report) — exposed as trace show and trace report. Replay is pure: data in, strings out, no subprocess or network.

Sandbox (Milestone 7)

The sandbox is the policy layer over the tools' mechanism. A SandboxPolicy declares allowed/denied read & write path globs, a command allow/denylist, a network flag, and runtime/output caps; a Sandbox enforces it on every agent tool call. check_call runs before dispatch — it extracts the path(s) a path tool would touch (apply_patch targets are parsed from the patch) or the program an exec tool would run, and returns an allow/deny PolicyDecision; a denied call is recorded as a "blocked" step and never executes. redact_result runs after — it scrubs credential-shaped output (file contents, stdout/stderr, diffs) using the same patterns as the commit-time hygiene scanner, so a captured secret never reaches a step, a trace, or the agent's next observation. Enforcement is on by default (RunConfig.enforce_sandbox) with permissive, task-derived defaults, and the effective policy is echoed into the RunResult. This reduces blast radius and adds observability — it is not a jail (program-name command matching, heuristic network denylist, no process/namespace isolation). See Sandboxing.

Current test/result status

Scaffold-layout, task-format, tool, and runtime tests pass under python3 -m pytest -q. tests/test_runtime.py covers the agent interface, workspace preparation, allowed-tool gating, scoring, and full runs: the scripted agent fixes the tiny_python_bug fixture end to end (failing → passing) and the final diff is captured, while the mock agent leaves it failing. Tests needing git skip when it is absent.

Open questions / limitations

  • The runtime enforces workspace confinement, capability gating, and the Milestone 7 sandbox policy (path/command/network gating, runtime/output caps, secret redaction) — but not process/namespace isolation. Command matching is by program name and network enforcement is heuristic; a containerized runner is a future option.
  • Scoring covers test_command and none only; the other methods and the suite/regression machinery are Milestone 8.
  • apply_patch applies exact-context unified diffs (no fuzzy matching, no binary patches, no rename detection).
  • What is the minimal trace schema that still supports faithful replay? replay_trace (Milestone 6) reconstructs the timeline, tool calls, diff, tests, and failure point from the current schema; a re-execution/verification mode is a later, optional capability.
