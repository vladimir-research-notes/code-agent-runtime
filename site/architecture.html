Brief explanation

The runtime is an explicit pipeline. Each stage has a clear input and output so that every step can be inspected, traced, and reproduced.

Design principles: deterministic-first, everything-is-traced, separation of policy and mechanism, and no hidden cost.

Core tools (Milestone 3)

Tools are the only way an agent acts on a workspace. Every tool shares one shape — a static ToolSpec, a validated run() entry point, and a JSON-serialisable ToolResult — so the runtime can dispatch them uniformly and the tracer can record them faithfully. A ToolRegistry maps names to tools and dispatches a ToolCall. Path-taking tools are confined to one workspace directory; subprocess tools bound their output and time and run without a shell.

ToolCategoryWhat it returns
read_filereadcontent, bytes, lines, binary/truncated flags
search_reporeadmatching lines (path/line/text), counts
git_diffreadunified diff, per-file +/- counts, untracked files
write_filewritebytes written, created vs. overwrote
apply_patchwriteper-file create/modify/delete, +/- counts
run_shellexecargv, exit code, stdout/stderr, timed-out flag
run_testsexecas run_shell, plus a passed boolean

The registry's REGISTERED_TOOL_NAMES is the authoritative tool vocabulary; a test asserts it equals the task schema's KNOWN_TOOLS, so a task can never request a tool that does not exist.

Runtime loop (Milestone 4)

The runtime turns a validated task and an agent into a single structured, scored RunResult. An agent only proposes the next action (run a tool, or finish); the runtime owns every side effect — preparing the workspace, gating each call against the task's allowed_tools, dispatching it, running the task's test command, capturing the final diff, scoring, and reporting. Two deterministic, model-free agents ship: mock (a null baseline that does nothing) and scripted (replays a fixed plan, with built-in solutions for the example tasks). Run one with code-agent-runtime run <task>.

load task -> prepare workspace -> [agent step -> gate -> execute tool]* -> run tests -> score -> report
StageWhat happens
prepare workspacecopy the fixture to a fresh temp dir; git init + commit
agent stepagent.propose(Observation) returns one AgentAction
execute toolgate against allowed_tools, then dispatch via the registry
run testsrun the task's test_command through the run_tests tool
scoredelegate to scoring.score_run (see Scoring below)
reportbuild the RunResult; render text or JSON

Containment is workspace confinement, allowed_tools capability gating, and the Milestone 7 sandbox policy (see below) — but no process/namespace isolation. The loop scores by delegating to the Milestone 8 scoring layer, before the workspace is cleaned up.

Trace recorder (Milestone 5)

A run can be recorded as a structured, JSON-serialisable Trace with two layers: a timestamped events timeline (run_started, workspace_prepared, tool_call, agent_finish, tests_ran, diff_captured, scored, run_finished) and the embedded result holding the full payloads (command stdout/stderr, the final diff, test results, exit status). The recorder owns the when — each event carries a wall-clock timestamp and a monotonic elapsed_seconds; the run carries started_at/finished_at/ duration_seconds. This is the one temporal artifact: tools and RunResult stay timing-free and deterministic. Tracing is opt-in — the loop records only when a recorder is passed (run_task(..., recorder=) / record_run / run --trace) — and the loop never imports the tracer, so an untraced run is unchanged. Captured output is not redacted yet (Milestone 7).

Trace replay (Milestone 6)

replay_trace(trace) reconstructs a run from a stored trace without re-executing it, into a ReplayedRun: the ordered timeline, the tool_calls extracted from it, the tests and diff payloads, every detected anomaly (a blocked or failed tool call, a failing test command, a run that errored), and the single failure point that best explains the verdict — a terminal run_error, then the scoring tests_failed, else the earliest anomaly. A run that passed or was not scored has no failure point, even with anomalies: that asymmetry surfaces a verdict that hid a failure mode. Two renderers print a reconstruction — summarize_trace (text) and trace_to_markdown (a Markdown report) — exposed as trace show and trace report. Replay is pure: data in, strings out, no subprocess or network.

Sandbox (Milestone 7)

The sandbox is the policy layer over the tools' mechanism. A SandboxPolicy declares allowed/denied read & write path globs, a command allow/denylist, a network flag, and runtime/output caps; a Sandbox enforces it on every agent tool call. check_call runs before dispatch — it extracts the path(s) a path tool would touch (apply_patch targets are parsed from the patch) or the program an exec tool would run, and returns an allow/deny PolicyDecision; a denied call is recorded as a "blocked" step and never executes. redact_result runs after — it scrubs credential-shaped output (file contents, stdout/stderr, diffs) using the same patterns as the commit-time hygiene scanner, so a captured secret never reaches a step, a trace, or the agent's next observation. Enforcement is on by default (RunConfig.enforce_sandbox) with permissive, task-derived defaults, and the effective policy is echoed into the RunResult. This reduces blast radius and adds observability — it is not a jail (program-name command matching, heuristic network denylist, no process/namespace isolation). See Sandboxing.

Scoring & reports (Milestone 8)

The scoring/ layer turns a finished run into a verdict and is a pure function of the evidence the run produced (the test result, the captured diff, the live workspace) — so a verdict is reproducible and unit-testable without re-running anything. The loop calls score_run, which dispatches on the task's scoring_method:

MethodPasses when…
test_commandthe test command exits 0 (a timeout fails).
expected_filesnamed files exist / are absent / contain text.
diff_constraintthe change stays within allowed_paths (and max_files, no forbidden paths, non-empty). Scope, not correctness.
customa named scorer from an in-code registry says so (e.g. tests_pass_and_diff_scope).
nonejudged by inspection → not_scored.

run_suite runs a task×agent matrix and returns a JSON-serialisable SuiteResult of per-run EvalRecords (task id, agent, pass/fail, runtime, tool/command counts, failure reason); reports/ renders it to Markdown or standalone HTML. Wall-clock timing lives in the suite layer so RunResult stays deterministic. The whole chain runs offline via code-agent-runtime eval run / scripts/02_generate_report.py. See Evals and Results.

Regression & flakiness (Milestone 9)

Two analyses sit above the suite layer, consuming the JSON SuiteResults it already emits — so neither re-runs an agent. compare_suites diffs a baseline result against a candidate, keyed by (task id, agent), and buckets every key on the pass/fail signal: improved (gained a pass), regressed (lost one), unchanged, added/removed (present on one side only); any other outcome transition is kept in detail. Rerun mode (run_repeated → analyze_flakiness) runs the same suite N times and flags any key whose scored outcome was not identical on every repeat — verdict flakiness ignores wall-clock runtime. The deterministic agents yield zero flaky keys, a determinism check the tests assert. Exposed as eval compare / eval rerun. See Evals and Results.

Optional cost-controlled LLM adapter (Milestone 10)

The agents/llm/ subpackage adds a model-backed llm agent that plugs into the same one-action-per-step contract the baselines use, so the runtime, tracer, and scorer treat it identically. It is built so the real provider is strictly optional: nothing imports a network library at load time. Each step funnels through the safety machinery in order — render and redact the next turn, check the response cache (a hit is free), and on a miss ask the budget guard to clear the call's worst case before contacting the client, then record the actual usage and parse the reply into one action.

ModuleResponsibility
client.pythe LLMClient seam, plus a deterministic offline FakeLLMClient.
pricing.pytoken estimation + an (approximate, overridable) model price table.
budget.pythe BudgetGuard: a hard pre-call ceiling; unpriced ⇒ refused.
cache.pycontent-hash response cache (memory + optional disk).
protocol.pyprompt building and parse_action (model text → one AgentAction).
agent.pyLLMAgent, the offline builder, and dry_run_plan.
claude_client.pythe real ClaudeAPIClient, lazily importing anthropic.

Disabled by default and offline by default: run --agent llm uses the fake client (solving tasks via their known-good solution through the wire format) unless --allow-paid opts into a real run; --dry-run previews the request and cost with no call. No test makes a paid call. See Evals.

Claude Code trace importer (Milestone 11)

The importers/ subpackage lets an external run enter the pipeline at the scoring step rather than the agent loop. It normalises a Claude-Code-like run into an ImportedRun (the external tool calls mapped onto this runtime's vocabulary, the change, and any declared outcome), then convert.import_to_run produces a RunResult + Trace scored by the same score_run and replayable with the same tooling.

ModuleResponsibility
schema.pyImportedRun/ImportedAction (validation, JSON round-trip), tool-name mapping.
diffs.pytree_diff / parse_unified_diff → the git_diff-shaped dict the scorers consume (no git needed).
sources.pythe four builders (before/after, diff + log, transcript, synthetic) and export_run.
convert.pyimport_to_run: trust/verify evidence, step synthesis, and canonical trace construction via the recorder.

Two scoring modes: verify reconstructs the workspace and re-runs the task's real test command (this runtime's measurement); trust scores the source's declared evidence. The imported process is preserved as the trace's steps in both. All offline — no model, no network. See Evals and Tracing & replay.

Reproducible case study (Milestone 12)

The case study points the whole pipeline at a real, if small, workload: 13 tasks across all five categories (bugfix, refactor, cli_change, tests_must_pass, security), each with a real fixture and a deterministic scripted solution (or a sandbox probe). scripts/07_case_study.py runs the mock (null) and scripted baselines plus the security probe with tracing on, then writes the result CSV the plan calls for (via a new suite_to_csv exporter), Markdown/HTML reports, and one inspectable trace per run — reloading and replaying one to prove inspectability. It exercises every scoring method and stays offline (no model, no paid API). The committed, runtime-free table lives at docs/results/case_study.csv; a test regenerates it and asserts a byte match so it cannot silently drift. See Results.

Current test/result status

The full CPU-only suite passes under python3 -m pytest -q — no model, no network, no API key. It spans the agent interface and runtime loop (the scripted agent fixes a fixture end to end while the null mock leaves it failing), the trace recorder and replay, every sandbox rule and the secret redactor, all scoring methods and the suite runner, the regression/flakiness buckets and the determinism check, the LLM adapter (offline), and the importer (round-trip + verify-catches-forgery). The Milestone 12 case study runs 13 tasks × the baselines into a committed, byte-stable CSV; a layout test asserts every required website page carries the six standard sections and links to the whole nav. Tests needing git skip when it is absent.

Open questions / limitations

  • The runtime enforces workspace confinement, capability gating, and the Milestone 7 sandbox policy (path/command/network gating, runtime/output caps, secret redaction) — but not process/namespace isolation. Command matching is by program name and network enforcement is heuristic; a containerized runner is a future option.
  • Scoring covers all four methods plus a custom registry and a suite runner (Milestone 8); regression comparison and flakiness across result files landed in Milestone 9. A passing test command is evidence, not proof, of correctness.
  • The LLM adapter's cost guard is bounded by its inputs: pricing is approximate (verify before a paid run; an unpriced model is refused) and token counts are a chars/4 heuristic; the offline fake replays a fixed solution, demonstrating the harness, not model reasoning.
  • apply_patch applies exact-context unified diffs (no fuzzy matching, no binary patches, no rename detection).
  • What is the minimal trace schema that still supports faithful replay? replay_trace (Milestone 6) reconstructs the timeline, tool calls, diff, tests, and failure point from the current schema; a re-execution/verification mode is a later, optional capability.
