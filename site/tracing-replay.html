Tracing & replay

A run that cannot be replayed from its trace is a bug, not a feature.

status: Milestone 6 — trace recorder and replay/summarise tooling implemented

Brief explanation

Every run can be recorded as a structured, JSON-serialisable trace: enough to reconstruct what the task was, what the agent did, what the runtime observed, and when — without re-executing anything. A trace is the evidence behind a reported result. Tracing is opt-in: an untraced run is byte-for-byte unchanged. Replay reads a stored trace back and reconstructs the action timeline, the tool calls, the diff, the tests, and the failure point — then renders it as a text summary or a Markdown report.

Deeper technical explanation

A trace has two layers. The events list is a timestamped timeline — run_started, workspace_prepared, tool_call, agent_finish, tests_ran, diff_captured, scored, run_finished — each carrying a sequence number, the run phase, a wall-clock timestamp, a monotonic elapsed_seconds, a one-line summary, and a compact payload. The embedded result (the run's RunResult) holds the full payloads exactly once: command stdout/stderr, the final unified diff, test results, and exit status. Events are the timeline; the result is the evidence they point into.

This is where wall-clock timing enters the system. Tools and RunResult are deliberately timing-free so they stay deterministic; the trace is the one temporal artifact. The recorder reads time through an injectable Clock (real time.time + time.monotonic in production; a deterministic fake in tests), so a traced run is fully reproducible under test.

Replay: reconstruction, not re-execution (Milestone 6)

replay_trace(trace) turns a stored trace back into a ReplayedRun: the ordered timeline, the tool_calls extracted from it (each with its allowed/blocked and ok/failed state and exit code), the tests and diff payloads, every detected anomaly, and the single failure point that best explains the verdict. It re-runs nothing — no workspace, no subprocess, no network — it reads the trace and interprets it.

The value over the raw trace is interpretation. A bare pass/fail verdict can hide failure modes that the timeline makes visible: a tool the permission gate blocked, a tool that returned an error, a failing test command, a run that errored before finishing. Replay records each as an anomaly and chooses the verdict-determining one (a terminal run_error, then the scoring tests_failed, else the earliest) as the failure point. A run that passed or was not scored has no failure point — even if it logged anomalies along the way. That asymmetry is the point: it surfaces a verdict that hid a failure mode, one of the project's research questions made concrete.

Two renderers print a reconstruction: summarize_trace (a compact one-screen text summary) and trace_to_markdown (a fuller Markdown report with the timeline, tool calls, test-output tail, and unified diff as headings and tables).

Current implementation status

Implemented (Milestones 5–6). The traces/ package defines the schema (Trace, TraceEvent, SCHEMA_VERSION) and a TraceRecorder the runtime loop drives stage by stage; record_run returns (result, trace) and write_trace/load_trace persist and reload a trace as JSON. replay_trace reconstructs a run, and summarize_trace / trace_to_markdown render it. From the CLI: run --trace [PATH] records, trace show <path> summarises (or --json emits the structured ReplayedRun), and trace report <path> writes a Markdown report.

Current test/result status

tests/test_traces.py covers the recorder and schema; tests/test_replay.py covers replay and rendering: a passing run (timeline, tool calls, counts, no failure point), a failing run (the mock agent leaves tests failing → tests_failed is the failure point), an errored run (workspace prep failed → run_error, a two-event timeline), a blocked tool call that is an anomaly but not the failure point on a passing run, the ReplayedRun JSON round-trip, the text/Markdown renderers (including pipe escaping in table cells), and the trace show / trace report CLI. Git-dependent diff assertions skip when git is absent.

Open questions / limitations

  • Redaction is heuristic. As of Milestone 7, when the sandbox is enabled (the default) the runtime scrubs credential-shaped strings from command stdout/stderr, file contents, and diffs before they enter a trace, so a recorded trace and the reports rendered from it are redacted with the same high-precision patterns as the hygiene scanner — which can miss novel or obfuscated secrets. With --no-sandbox no redaction occurs; treat such traces as unredacted. The default traces/ destination is gitignored.
  • Replay reconstructs; it does not re-execute. A mode that re-runs a trace to confirm it reproduces is a later, optional capability.
  • trace show / trace report are inspectors: they exit non-zero only on a missing/malformed trace, not on a failed run.
