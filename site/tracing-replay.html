Tracing & replay

A run that cannot be replayed from its trace is a bug, not a feature.

status: Milestone 5 — trace recorder implemented; replay/summarise tooling is Milestone 6

Brief explanation

Every run can be recorded as a structured, JSON-serialisable trace: enough to reconstruct what the task was, what the agent did, what the runtime observed, and when — without re-executing anything. A trace is the evidence behind a reported result. Tracing is opt-in: an untraced run is byte-for-byte unchanged.

Deeper technical explanation

A trace has two layers. The events list is a timestamped timeline — run_started, workspace_prepared, tool_call, agent_finish, tests_ran, diff_captured, scored, run_finished — each carrying a sequence number, the run phase, a wall-clock timestamp, a monotonic elapsed_seconds, a one-line summary, and a compact payload. The embedded result (the run's RunResult) holds the full payloads exactly once: command stdout/stderr, the final unified diff, test results, and exit status. Events are the timeline; the result is the evidence they point into.

This is where wall-clock timing enters the system. Tools and RunResult are deliberately timing-free so they stay deterministic; the trace is the one temporal artifact. The recorder reads time through an injectable Clock (real time.time + time.monotonic in production; a deterministic fake in tests), so a traced run is fully reproducible under test. Replay and summarise tooling — reconstructing the action timeline, diffs, tests, and failure point from a stored trace without re-executing — is Milestone 6.

Current implementation status

Implemented (Milestone 5). The traces/ package defines the schema (Trace, TraceEvent, SCHEMA_VERSION) and a TraceRecorder the runtime loop drives stage by stage. record_run returns (result, trace); write_trace/load_trace persist and reload a trace as JSON; and code-agent-runtime run --trace [PATH] records a run from the CLI.

Current test/result status

tests/test_traces.py passes: schema round-trip, recorder lifecycle (event order, sequence, elapsed), record_run over the shipped fixtures (full timeline, embedded result, deterministic id and timestamps via a fake clock), the error path, JSON persistence (file and directory), and the run --trace CLI. Git-dependent assertions (the diff_captured event) skip when git is absent.

Open questions / limitations

  • Captured output is not redacted. A trace stores command stdout/stderr as captured, so it may contain whatever a command printed (including secrets). Redaction belongs with the secret scanner in Milestone 7; until then, do not persist traces of untrusted commands to a shared location.
  • Is the event/result split (timeline vs. payloads) the right boundary for faithful replay? Milestone 6 will tell.
  • default_trace_id is best-effort unique (<task>-<wall.3f>); pass an explicit id when a hard guarantee is needed.
