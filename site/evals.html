Evals

Reproducible, inspectable, honest measurement — not a leaderboard.

status: implemented (Milestones 8–12) — scoring, suite runner, Markdown/HTML/CSV reports, regression & flakiness, optional LLM adapter, Claude Code trace importer, reproducible case study

Brief explanation

An eval runs one or more agents over a suite of tasks and scores each run. Deterministic mock and scripted baselines establish a floor and exercise the harness without any model. The result is a table — one row per run — that serialises to JSON and renders to Markdown, HTML, or CSV. The Milestone 12 case study is the headline run: 13 tasks across all five categories.

Deeper technical explanation

Scoring is a pure function of the evidence a run already produced (the test result, the captured diff, the live workspace), so a verdict is reproducible and unit-testable without re-running anything. Five scoring methods, selected per task by scoring_method (with method-specific scoring_config):

MethodPasses when…
test_commandthe test command exits 0 (a timeout fails).
expected_filesnamed files exist / are absent / contain text.
diff_constraintthe change stays within allowed_paths (and max_files, no forbidden paths, non-empty). A constraint, not a correctness check.
customa named scorer from an in-code registry says so; the shipped tests_pass_and_diff_scope combines correctness with scope.
nonenot auto-scored (judged by inspection, e.g. the sandbox demo) — reported not_scored.

Each run records the plan's result fields: task id, agent, pass/fail, runtime (wall-clock, measured by the suite layer so the run record stays deterministic), tool-call count, command count, and a failure reason. Build artifacts (__pycache__, *.pyc) are ignored in diff-scope analysis. Run it:

code-agent-runtime eval run --dir tasks                 # Markdown report
code-agent-runtime eval run --dir tasks --json          # machine-readable result
code-agent-runtime eval run --dir tasks --out r.json --report r.csv   # CSV (also .html)
code-agent-runtime eval report r.json --format csv      # re-render a saved result as CSV
python3 scripts/07_case_study.py                        # the case study: CSV + reports + traces

Regression comparison & flakiness (Milestone 9)

Two analyses over the result files above. compare_suites diffs a baseline result against a candidate, keyed by (task id, agent), and buckets every key. The headline signal is pass/fail: improved = gained a pass, regressed = lost one; any other outcome change (e.g. failed → error) is unchanged with the transition kept in detail. A key that flipped across repeats is flaky; a key present on only one side is added/removed.

BucketMeaning
improvedthe key gained a pass it did not have.
regressedthe key lost a pass it had (the natural CI gate).
unchangedneither gained nor lost a pass.
flakya side's repeated runs disagreed on outcome.
added / removedthe key exists in only one of the two files.

Flakiness is measured by re-running the same suite N times (rerun mode) and flagging any key whose scored outcome was not identical on every repeat. Verdict flakiness ignores wall-clock runtime; tool/command-count variation with a stable verdict is reported as a signal difference, not a flake. The deterministic mock/scripted/probe agents produce zero flaky keys — a determinism check the tests assert.

code-agent-runtime eval rerun --dir tasks --repeats 3      # flakiness report (exit 1 if any flake)
code-agent-runtime eval compare base.json cand.json        # regression report (exit 1 if any regression)
python3 scripts/03_regression_demo.py                      # one-shot demo, writes results/

A “0 regressions” comparison means no key lost a pass relative to the baseline — not that the candidate is correct. Because the deterministic baseline cannot regress against itself, the regressed and flaky buckets are demonstrated on synthetic “fake agent versions” in the tests. See Results.

Optional cost-controlled LLM adapter (Milestone 10)

A model-backed llm agent plugs into the same one-action-per-step contract the deterministic baselines use, wrapped in the safety machinery a paid run requires. It is disabled and offline by default: with no --allow-paid it is driven by a deterministic fake client that replays a task's known-good solution through the model wire format, so the whole path (prompt → parse → action → tool → score) runs — and the guard, cache, and redaction are exercised — with no API key and no spend.

ControlWhat it does
Hard pre-call budget guardprices each call's worst case (estimated input + full max_tokens output) and refuses before the call if it could exceed --max-cost-usd; an unpriced model is refused, not guessed.
Response cacheidentical requests (content hash) are served free; re-runs don't re-spend.
Transcript redactioncredential-shaped text is scrubbed from what is sent to and stored from the model (reusing the sandbox secret scanner).
--dry-runprints the first request and its estimated worst-case cost; makes no call and spends nothing.
--allow-paidopt-in to a real Claude API run (needs the [claude] extra, ANTHROPIC_API_KEY, and a budget). The real client lazily imports anthropic.
code-agent-runtime run bugfix/sum-range-off-by-one --agent llm            # offline solve, no key
code-agent-runtime run bugfix/sum-range-off-by-one --agent llm --dry-run  # cost preview, no call
python3 scripts/05_llm_adapter_demo.py                                    # offline tour, writes results/

Pricing is approximate published list pricing that must be verified before a paid run; the offline fake replays a fixed solution, so it demonstrates the harness and the cost guard, not genuine model reasoning. See Results for the offline demo numbers.

Scoring an external run: the Claude Code trace importer (Milestone 11)

To compare a Claude-Code-like run against these agents, that external run must be scored the same way. The importers/ package normalises four input forms — before/after directories, a diff + command log, an exported transcript, or a deterministic synthetic run — into one ImportedRun, then import_to_run converts it into a RunResult + Trace scored by the same score_run and replayable with the same tooling as a native run.

ModeHow the verdict is reached
verifyreconstruct the workspace from the imported after-state over the task fixture and run the task's real test command (and capture a real diff) — this runtime's own measurement.
trustscore the source's declared diff/test result — fast, but it believes the source; the only option when the import carries no file content.
autoverify when the after-state and fixture are available, else fall back to trust (and say which happened).
code-agent-runtime import synthesize bugfix/sum-range-off-by-one --out results/raw/src.json
code-agent-runtime import show results/raw/src.json          # summarise the import source
code-agent-runtime import run results/raw/src.json --trace traces/   # convert + score (auto)
code-agent-runtime import run results/raw/src.json --mode trust      # score declared evidence
python3 scripts/06_import_demo.py                            # offline tour, writes results/

The payoff is honesty under measurement: a broken change carrying a forged “tests passed” scores passed in trust mode but failed in verify mode — verify measures what trust only believes. It is all offline (no model, no network). See Results for the demo numbers.

Reproducible case study (Milestone 12)

The case study is the platform pointed at a real, if small, workload: 13 tasks across all five categories (bugfix, refactor, cli_change, tests_must_pass, security), each with a deterministic scripted solution or a sandbox probe. scripts/07_case_study.py runs both baselines plus the probes with tracing on, then writes the result CSV the plan calls for, Markdown/HTML reports, and one inspectable trace per run — and proves a trace is inspectable by reloading and replaying one. The result table renders as CSV via the new suite_to_csv exporter (the deterministic, runtime-free form is committed at docs/results/case_study.csv; the under-results/ form includes wall-clock runtime).

The optional imported Claude Code run and cost-controlled API run the plan mentions are demonstrated by the importer (M11) and LLM-adapter (M10) sections above and are intentionally not part of this committed, model-free baseline. See Results for the full matrix.

Current implementation status

Implemented. scoring/ provides the five scorers, the custom-scorer registry hook, the suite runner (run_suite → a JSON SuiteResult), rerun mode (run_repeated), and the regression/flakiness analyses (compare_suites, analyze_flakiness in regression.py); reports/ renders Markdown and standalone HTML for suites, and Markdown for comparisons and flakiness. The runtime loop delegates scoring to this layer, scoring before the workspace is cleaned up so filesystem checks work. See Results for the real baseline numbers.

Current test/result status

tests/test_scoring.py unit-tests every scorer (pass and fail paths, edge cases) and the scoring_config schema validation; tests/test_eval.py covers the suite runner, JSON round-trip, the Markdown/HTML reports, and the eval CLI; tests/test_regression.py covers every comparison bucket on synthetic agent versions, flakiness detection, the determinism check (re-running the real suite → zero flaky keys), the JSON round-trips, the Markdown reports, and the eval compare / eval rerun CLI. tests/test_llm_adapter.py covers the LLM adapter end to end — token/cost estimation, the pre-call budget guard (including a refused over-budget call), the response cache (memory + disk persistence), transcript redaction, dry-run, the wire protocol, the offline solve, and the CLI — all with no network and no API key. The full CPU-only suite passes. The baseline run shows the scripted agent passing every solvable task and the mock agent failing the ones that require a change.

Open questions / limitations

  • Small task counts make results illustrative, not statistically powerful.
  • A passing test command is evidence, not proof, of a correct change — and is bounded by the fixture's test coverage (see the Results caveats).
  • diff_constraint checks scope, not correctness; combine via a custom scorer.
  • Two single-run files can't reveal flakiness; flakiness needs repeats. Regression/flakiness reports are Markdown + JSON only this milestone (no standalone HTML yet).
  • The LLM cost guard is bounded by its inputs: pricing is approximate (verify before a paid run; an unpriced model is refused) and token counts are a chars/4 heuristic. The offline fake agent replays a fixed solution — a harness exercise, not model reasoning.
  • An imported run's trust mode scores the source's declared evidence — only as trustworthy as the source; verify mode re-runs the real test command but needs the after-state and the task fixture. Reconstructed diff line-counts are best-effort (verification does not depend on them). The synthetic run is a scripted solution, not model capability.
