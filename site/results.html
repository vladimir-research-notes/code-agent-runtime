Honest caveats

  • A passing test command is evidence, not proof. cli/add-shout-flag (the test_command variant) passes under the mock agent even though the mock changes nothing — the fixture's tests do not exercise the new --shout flag. The cli/add-shout-flag-custom variant is the discriminating version: its custom scorer requires the tests to pass and an in-scope change.
  • diff_constraint scores scope, not correctness, and fails an empty change by default.
  • Small task counts make this illustrative, not a benchmark.

Regression & flakiness (Milestone 9)

Two analyses over the result files above, produced by scripts/03_regression_demo.py (or eval rerun / eval compare) — CPU-only and model-free.

Flakiness. Re-running the whole suite three times and aggregating the verdicts gives 3 repeats over 12 keys — 0 flaky, 12 stable. A key is flaky iff its scored outcome was not identical on every repeat; the deterministic agents have none, and their tool/command counts match across repeats too. This is a determinism check the tests assert, not a claim.

Regression. Comparing the null mock baseline against the scripted solver as two “agent versions” (keyed by task) gives 6 keys — 4 improved, 0 regressed, 1 unchanged, 0 flaky, 0 added, 1 removed:

The solver improves every task the null baseline fails; nothing regresses. The security demo is removed because the scripted agent has no solution for it (that pair is skipped), so the key exists only on the baseline side — surfaced honestly, not dropped. Because the deterministic baseline cannot regress against itself, the regressed and flaky buckets are demonstrated on synthetic “fake agent versions” in tests/test_regression.py; the rule is narrow — improved = gained a pass, regressed = lost a pass.

Offline demos: LLM adapter (M10) & Claude Code importer (M11)

Two model-free, no-spend demos extend the baseline. The LLM-adapter demo (scripts/05_llm_adapter_demo.py) exercises the cost guard, cache, and redaction with a deterministic fake client. The importer demo (scripts/06_import_demo.py) synthesizes a Claude-Code-like run, then scores it both ways: trust mode believes the source's declared result; verify mode re-runs the task's real test command. The headline is the last row — a broken change with a forged “tests passed” is scored passed in trust mode but failed in verify mode, because verify measures what trust only believes. Full numbers and the table are in docs/RESULTS.md.

Open questions / limitations

Results are illustrative on small task sets. A “0 regressions” comparison means no key lost a pass relative to the baseline — not that the candidate is correct. Flakiness here is a small-sample smoke check, not a flake-probability estimate.
