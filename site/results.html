Results

A real, reproducible case study — produced by the suite runner, not hand-written.

status: reproducible case study (Milestone 12); regression/flakiness (M9); offline LLM-adapter & importer demos (M10–M11)

Brief explanation

The Milestone 12 case study runs the deterministic baseline agents (mock the null baseline, scripted the solver, and probe on the two security tasks) over 13 small but genuine tasks across all five plan categories. Every scoring method is exercised, and each run leaves an inspectable trace. The numbers are regenerated by python3 scripts/07_case_study.py (or code-agent-runtime eval run --dir tasks); no model and no paid API are involved.

Deeper technical explanation

Every number on this page is produced by the tested suite runner, not hand-written. A run's verdict and its tool/command counts are pure functions of the evidence the run captured, so they are deterministic and reproduce byte-for-byte across machines; wall-clock runtime is the one machine-dependent column and is therefore omitted from the committed table (it stays in the generated CSV/report). The figures below are aggregated three ways — the headline case-study matrix, a flakiness pass that re-runs the suite and checks the verdicts are identical, and a regression comparison that treats the two baselines as “agent versions.” A test regenerates the committed docs/results/case_study.csv from a fresh run and asserts a byte match, so the published table cannot silently drift from the code.

Honest caveats

  • A passing test command is evidence, not proof. cli/add-shout-flag (the test_command variant) passes under the mock agent even though the mock changes nothing — the fixture's tests do not exercise the new --shout flag. The cli/add-shout-flag-custom variant is the discriminating version: its custom scorer requires the tests to pass and an in-scope change.
  • diff_constraint scores scope, not correctness, and fails an empty change by default.
  • Small task counts make this illustrative, not a benchmark.

Regression & flakiness (Milestone 9)

Two analyses over the result files above, produced by scripts/03_regression_demo.py (or eval rerun / eval compare) — CPU-only and model-free.

Flakiness. Re-running the whole case-study suite three times and aggregating the verdicts gives 3 repeats over 26 keys — 0 flaky, 26 stable. A key is flaky iff its scored outcome was not identical on every repeat; the deterministic agents have none, and their tool/command counts match across repeats too. This is a determinism check the tests assert, not a claim.

Regression. Comparing the null mock baseline against the scripted solver as two “agent versions” over the full case study (keyed by task) gives 13 keys — 10 improved, 0 regressed, 1 unchanged, 0 flaky, 0 added, 2 removed. The solver improves every task the null baseline fails; nothing regresses. The two security demos are removed because the scripted agent has no solution for them (those pairs are skipped), so the keys exist only on the baseline side — surfaced honestly, not dropped. Because the deterministic baseline cannot regress against itself, the regressed and flaky buckets are demonstrated on synthetic “fake agent versions” in tests/test_regression.py; the rule is narrow — improved = gained a pass, regressed = lost a pass.

Offline demos: LLM adapter (M10) & Claude Code importer (M11)

Two model-free, no-spend demos extend the baseline. The LLM-adapter demo (scripts/05_llm_adapter_demo.py) exercises the cost guard, cache, and redaction with a deterministic fake client. The importer demo (scripts/06_import_demo.py) synthesizes a Claude-Code-like run, then scores it both ways: trust mode believes the source's declared result; verify mode re-runs the task's real test command. The headline is the last row — a broken change with a forged “tests passed” is scored passed in trust mode but failed in verify mode, because verify measures what trust only believes. Full numbers and the table are in docs/RESULTS.md.

Current test/result status

The numbers above are produced by the tested suite runner; the verdicts and tool/command counts are deterministic across machines. CPU-only tests pass, including the regression/flakiness suite that asserts every comparison bucket and zero flaky keys on the real suite.

Open questions / limitations

Results are illustrative on small task sets. A “0 regressions” comparison means no key lost a pass relative to the baseline — not that the candidate is correct. Flakiness here is a small-sample smoke check, not a flake-probability estimate.
