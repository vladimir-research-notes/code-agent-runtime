Security model

Honest framing: this is not a production-grade sandbox.

status: threat model documented; repo hygiene scanner live (M1); runtime sandbox controls live (M7)

A capable adversary, or an agent running with broad host permissions, can escape the controls described here. The goal is blast-radius reduction and observability for semi-trusted, deterministic agents on a developer machine.

Brief explanation

The security model protects developer secrets, files outside the workspace, the network, and the host from destructive commands — against bugs and over-eager agents, not against deliberately malicious native code.

Deeper technical explanation

In scope

  • An agent that reads or writes outside its workspace.
  • An agent that runs a dangerous shell command by mistake.
  • Accidental secret capture into traces or reports.

Out of scope

  • A deliberately malicious agent with native code execution and kernel exploits.
  • Side-channel, timing, or hardware attacks.
  • Multi-tenant isolation guarantees.

Current implementation status

Two layers of control are live. Runtime containment (Milestone 7): a SandboxPolicy + Sandbox enforced by default on every agent tool call — allowed/denied read & write paths, command allow/denylist, a network flag (default off, enforced by denying known network programs), runtime/output caps, and a secret scanner that redacts credential-shaped output before it lands in a trace. See Sandboxing. Commit-time hygiene (Milestone 1): the .gitignore / .claude/settings.json deny rules, the no-secrets-committed principle, and the repository hygiene scanner that flags secrets, virtualenvs, caches, node_modules, large files, result blobs, model weights, and a committed .claude/settings.local.json. Both the runtime redactor and the commit-time scanner use the same heuristic secret patterns. This is not a jail — command matching is by program name, network enforcement is heuristic, and there is no process/namespace isolation — see Limitations.

Current test/result status

CPU-only tests cover both layers: tests/test_sandbox.py asserts blocked-vs-allowed behaviour on the unsafe-command demo (every host-escaping action blocked with its rule, the benign read allowed) and the secret redactor; tests/test_hygiene.py covers the commit-time scanner, including a guard that scans the committed tree and asserts it is clean.

Open questions / limitations

  • How much isolation is achievable without containers or root? (Today: none beyond policy + workspace confinement.)
  • What is the right default network posture for scripted vs. LLM agents?
  • Should the command policy move from program-name matching to an executed-path allowlist?
