Sandboxing

Blast-radius reduction and observability for semi-trusted agents.

status: Milestone 7 — implemented; enforced by default on every run

This is not a production-grade sandbox. The goal is to reduce accidental damage and make actions observable — not to contain malicious native code. Command matching is by program name, network enforcement is a heuristic denylist, and there is no process/namespace isolation. See Security.

Brief explanation

The sandbox is the policy layer over the tools' mechanism. A SandboxPolicy declares what an agent may read, write, and run; a Sandbox enforces it — gating each agent tool call before it runs (a denied call never executes) and redacting credential-shaped output after. It is enforced by default in the runtime loop, with permissive, task-derived defaults so ordinary runs are unchanged.

Deeper technical explanation

Containment primitives (all implemented):

PrimitiveHow it is enforced
allowed / denied read & write pathsworkspace-relative glob match per tool call; denied_paths (e.g. .env, .git, .aws, *.pem) wins over allow
command allowlist / denylistmatch the program name (argv[0] basename); default denylist blocks rm, sudo, dd, shutdown, …
network policy flagdeny well-known network programs (curl, wget, ssh, …) when network is off (default)
max runtime / max outputwall-clock and byte caps applied through the ToolContext
secret scannerredact credential-shaped output (file contents, stdout/stderr, diffs) before it enters a step, a trace, or the agent's next observation

The path/command extraction is explicit per tool: read_file/write_file by their path, apply_patch by its parsed target paths, and run_shell/run_tests by their command. A denied call is recorded as a "blocked" step carrying the rule (e.g. denied_path, outside_workspace, command_denylist, network_denied) — so the trace shows exactly what was blocked and why.

Unsafe demos (blocked vs. allowed)

Two built-in probe agents attempt the actions a coding agent must never perform, so the sandbox can be observed refusing them. Run them:

code-agent-runtime run security/unsafe-command-demo --agent probe
code-agent-runtime run security/secret-read-demo --agent probe

security/unsafe-command-demo covers the broad classes — reading .env (denied_path), reading ~/.aws/credentials and /etc/shadow (denied_path/outside_workspace), writing outside the workspace (outside_workspace), rm -rf . (command_denylist), and a curl egress (network_denied). security/secret-read-demo is the credential-exfiltration scenario — reading .env, an SSH key under .ssh/, and a *.pem key (all denied_path), reading /etc/passwd (outside_workspace), and uploading with scp / curl (network_denied). Both block every unsafe step while the benign in-workspace read still succeeds. Add --no-sandbox to disable enforcement.

Current implementation status

Implemented (Milestone 7). The sandbox/ package defines SandboxPolicy (and its default deny/allow vocabularies), the Sandbox enforcer (check_call + redact_result), and a secret scanner that reuses the hygiene scanner's patterns. The runtime enforces it on every agent tool call when RunConfig.enforce_sandbox is on (the default) and echoes the effective policy into the RunResult and trace. The repository hygiene scanner (Milestone 1) remains a separate commit-time guard.

Current test/result status

tests/test_sandbox.py (41 tests) covers the policy, the path/command matchers, every check_call rule, the secret scanner, gated dispatch (a denied call does not run; an allowed read is redacted), and the probe run end to end — every unsafe action blocked with the expected rule, the benign read allowed, nothing escaping the workspace. No destructive command is executed (the probe's rm/curl are blocked before dispatch).

Open questions / limitations

  • Command matching is by program name; a renamed binary or absolute path to a copy is not caught.
  • Network enforcement is heuristic — a direct socket open (e.g. python3 -c "import socket…") is not blocked.
  • No process/namespace isolation yet; a containerized runner for stronger isolation is a future, optional capability.
  • cpu_seconds is enforced as a wall-clock bound, not true CPU time.
